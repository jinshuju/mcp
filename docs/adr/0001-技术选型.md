# ADR-0001：金数据独立 MCP Server 的技术选型

- 状态：提议（2026-10-09）
- 任务：[T17266 船新的 MCP: github/jinshuju/mcp](https://qunli.co/2025/T17266)
- 背景：[D19350 All New API v1 立项文档](https://qunli.co/2025/D19350)

## 1. 要解决什么

立项文档对新 MCP 的要求，逐条对应到本方案：

| 立项目标                   | 本方案的落地                                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------------------------- |
| 1 API v1 提供 openapi.yaml | 已有（113 个操作、223 个 schema、540 KB）；本仓库以它为唯一事实来源                                      |
| 2 参数有校验               | MCP SDK 按 openapi 派生的 JSON Schema 校验入参，不合法不发请求；服务端 openapi_first 是第二道            |
| 3 输出有类型               | 2xx 响应 schema → `outputSchema` + `structuredContent`（小的随 tools/list 下发，大的 `get_schema` 可查） |
| 4 接口有描述               | `summary` + `description` 原样进工具描述；描述只在 openapi.yaml 里维护一份                               |
| 5 报错有详情               | HTTP 状态 + `error_description` + 逐条 `errors[]` + `X-API-Input-Warnings` + 一句怎么办                  |
| 6 MCP 能瘦身               | 同样的 60 个工具：内置 MCP ≈ 85k token → 本方案 ≈ 39k（o200k 实测，见 §3），靠大 schema 指针化与联合折叠 |
| 7 MCP 有测评               | 本 ADR §7 给出评测方案，作为后续任务                                                                     |

同时要替代现有的 builtin MCP（`https://jinshuju.net/mcp`，Rails gem 实现，协议 2025-06-18）。

## 2. 候选方案

业界把「API → MCP」分成四类，加上我们自己的两个参照物：

| 方案         | 代表                                                                                                                                                                                   | 怎么工作                                                        | 优点                            | 对我们的问题                                                                                                                                  |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| A 手写工具   | 现有 builtin gem；[qunli-mcp](https://github.com/jinshuju/qunli-mcp)                                                                                                                   | 每个工具一段 zod + 描述                                         | 描述可精雕细琢                  | 与 API v1 两套体系、靠 code review 同步（立项文档列的困境本身）                                                                               |
| B 运行时代理 | [openapi-mcp](https://github.com/jedisct1/openapi-mcp)（Go）、FastMCP `from_openapi`（Python）、[@ivotoby/openapi-mcp-server](https://github.com/ivo-toby/mcp-openapi-server)          | 启动时读 spec，一个 op 一个工具                                 | 零代码                          | 语言栈不对；工具名 / 体积 / 请求体形状不可控；FastMCP 自己也说只适合原型                                                                      |
| C 构建期生成 | [openapi-mcp-generator](https://github.com/harsha-iiiv/openapi-mcp-generator)、[Speakeasy](https://www.speakeasy.com/blog/generate-mcp-from-openapi)、Stainless（2026-01 前）          | 生成一个你拥有的 TS 项目                                        | 代码可控、可 CI                 | 产物基于 SDK v1、无 schema 瘦身、无 outputSchema；Speakeasy AGPL + SaaS 配置；仍要大量二次开发                                                |
| D Code Mode  | [Cloudflare mcp](https://github.com/cloudflare/mcp)、[Stainless（2026-01 起仅此一种）](https://www.stainless.com/changelog/mcp-servers-now-support-code-mode-only)、Docker Dynamic MCP | 只有 `search` + `execute` 两个工具，模型写 JS/TS 在沙箱里调 API | 固定 ≈ 1k token，一次调用串多步 | 需要沙箱（Cloudflare Dynamic Workers 2026-03 起 open beta、仅付费；Stainless 本地走 Deno 子进程）；弱模型写代码出错率高；与自有机房部署不匹配 |
| E 托管平台   | Speakeasy Gram、Zuplo、Scalar                                                                                                                                                          | SaaS 代管                                                       | 省运维                          | 数据与鉴权经第三方；国内访问                                                                                                                  |

选型时还核实了两个会改变前提的事实：

1. **MCP 规范已到 2026-07-28（当前版）**：去掉了 session 和 initialize 握手，每个请求自带协议版本；
   TypeScript SDK 相应出了 v2（`@modelcontextprotocol/server` 2.3.1，2026-07-27 起为 stable），v1.x 只维护 6 个月。
   qunli-mcp 用的 `McpAgent`（Durable Objects）已被 Cloudflare 标记为 legacy，官方建议新服务用无状态的 `createMcpHandler`。
2. **金数据已经有标准 OAuth 2.1 授权服务器**（`account.jinshuju.net`：动态注册、PKCE、refresh、RFC 8414 元数据），
   builtin MCP 就是靠它工作的。新 MCP 不需要再自建 OAuth（qunli-mcp 用 workers-oauth-provider + 贴 API Key 页面的那一套可以整个省掉）。

## 3. 度量：token 到底花在哪

用同一把尺子（tiktoken o200k，Claude 的分词对中文会更贵，但相对比例一致）量 `tools/list`：

| 工具集                                           | 工具数              | token      | 说明                                                                                       |
| ------------------------------------------------ | ------------------- | ---------- | ------------------------------------------------------------------------------------------ |
| builtin MCP（现状）                              | 60                  | 85,177     | `edit_form` 13.5k、`create_form` 8.8k；另有 52 个 resource、7 个 prompt                    |
| openapi 直译（一 op 一工具，全内联）             | 113                 | 144,060    | `updateForm` 29.6k、`updateTable` 29.5k、`createForm` 24.2k：三个工具占 58%                |
| 同上，大 schema 指针化                           | 113                 | 54,430     | FieldInput / FieldUpdateInput / FormSetting* / Theme* / View* 等 20 个 schema 改为一句指针 |
| 指针化 + 剔除 18 个不该暴露的操作                | 95                  | 43,681     | 估算值（第一版，后改为与 builtin 对齐）                                                    |
| **本方案实际 tools/list（与 builtin 一一对齐）** | **60 + get_schema** | **38,692** | 含 outputSchema（3.0k）；不含为 35.7k。edit_form 13.5k → 1.5k，create_form 8.8k → 0.6k     |
| Code Mode                                        | 2                   | ≈ 1,000    | 参照 Cloudflare 的数字                                                                     |

结论：**体积问题不在工具数量，在少数几个按 type 分支的大 schema**。把它们拿出工具定义、改成按需读取，
就从 85k 降到 39k（-55%，同一批 60 个工具）；再往下要么按产品取舍工具，
要么靠客户端的按需加载（Claude Code / Claude API 的 tool search 已默认支持），要么 Code Mode。

## 4. 决定

**自研一个薄的构建期生成器 + MCP SDK v2 + Hono，一份代码跑 Node（官方部署）、Cloudflare Workers（可选）和本地 stdio；
鉴权只做 Resource Server；Code Mode 作为第二阶段的可选 profile。**

| 关键决策      | 选择                                                                                                                                                                                          | 理由                                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 语言 / 运行时 | TypeScript，Node ≥ 20；ESM                                                                                                                                                                    | 与 qunli-mcp、jinshuju/cli、open-doc 同栈；SDK v2 要求 Node 20                                                     |
| MCP SDK       | `@modelcontextprotocol/server` v2（2026-07-28）                                                                                                                                               | 当前 stable；无状态；`fromJsonSchema` 直接吃 openapi 派生的 JSON Schema，不用再翻译成 zod；旧握手客户端由 SDK 兜底 |
| HTTP 框架     | Hono（`@modelcontextprotocol/hono` 适配）                                                                                                                                                     | Node / Workers / Bun 同一份 app；SDK 官方适配                                                                      |
| 工具生成      | 自研 `scripts/generate.ts`（约 300 行）+ `mcp.overlay.yaml`                                                                                                                                   | 现成生成器都要大改且基于 SDK v1；自研可精确控制：指针化、body 键名、注解、scope 抽取、outputSchema 阈值            |
| 生成时机      | 构建期，产物提交进仓库                                                                                                                                                                        | PR 里能 review 工具 diff；运行时不解析 YAML；CI 保证不漂移                                                         |
| 工具形态      | 与 builtin 的 60 个工具一一对齐（名字相同）：54 个一对一映射到操作，1 个投影（edit_field_rules = edit_form 的 field_rules），5 个组合（考试 / 测评建改各两步、count_entries 单 / 多表单分发） | 目标只是替换 builtin，不新增工具；对齐表就是 overlay 的 include，可 review                                         |
| 大 schema     | 指针化 + `get_schema` 工具 + `jinshuju://schemas/{name}` 资源；内联的按 type 分支联合折叠成公共属性 + 分支名；服务端专用的 if/then 约束 omit                                                  | 见 §3；形状校验交给服务端（openapi_first）                                                                         |
| outputSchema  | 压缩后 ≤ 700 字符的随 tools/list 下发；其余描述里留名字                                                                                                                                       | 全部下发要多 25k token；绑定「永远通过」的 validator，spec 与线上偶有出入时不把成功调用变成错误                    |
| 鉴权（HTTP）  | 纯 Resource Server：PRM 指向 account.jinshuju.net；Bearer 原样转 API；`GET /me` 校验并按令牌哈希缓存 5 分钟                                                                                   | 不签发令牌、无 KV / DO；个人 / 企业 Access Token 与 OAuth 令牌一视同仁；校验缓存避免每次工具调用多花一次 API 配额  |
| 鉴权（stdio） | `JINSHUJU_ACCESS_TOKEN` 或 `~/.jinshuju/config.json`（与 cli 共用，含 refresh）                                                                                                               | 一次 `jinshuju auth login` 两边都能用                                                                              |
| 部署          | Node + Docker 为主；Workers 可选                                                                                                                                                              | 现有 MCP / API 都在自有机房，国内访问稳定；无状态所以两边都只是一个 fetch handler                                  |
| 自动更新      | `spec-sync.yml` 每天拉 openapi.yaml → 重新生成 → 开 PR                                                                                                                                        | 「通过 openapi.yaml 自动更新 jinshuju/mcp」的实现                                                                  |
| 发布          | release-please + npm OIDC（抄 cli）                                                                                                                                                           | 零 token 存储                                                                                                      |
| 质量工具      | oxlint / oxfmt / node:test（抄 cli）                                                                                                                                                          | 零运行时依赖之外只有 SDK、Hono                                                                                     |

### 与 qunli-mcp 技术栈的差异

|          | qunli-mcp                                                     | jinshuju/mcp                           |
| -------- | ------------------------------------------------------------- | -------------------------------------- |
| SDK      | v1.12 `server.tool()` + zod                                   | v2 `registerTool()` + `fromJsonSchema` |
| 远程运行 | `McpAgent`（Durable Objects）+ `workers-oauth-provider`（KV） | `createMcpHandler`（无状态）；无绑定   |
| 鉴权     | 自建 OAuth，授权页让用户贴 API Key                            | 复用 account.jinshuju.net；Bearer 直通 |
| 工具来源 | 手写 46 个                                                    | openapi.yaml 生成 95 个                |
| 部署     | 仅 Workers                                                    | Node/Docker + Workers                  |

## 5. 不选 Code Mode 作为第一阶段的原因（以及什么时候加）

Code Mode 是 2026 年大 API 的主流（Stainless 直接砍掉了其它形态），但对金数据现在不是最优：

- 113 个操作是中等规模，指针化后 44k 已可接受，且 Claude Code / Claude API 的 tool search 会把工具定义延迟加载；
- 用户里有很多非开发者，在 claude.ai / Cursor / 国产模型客户端上用；让模型写 JS 调 API 的成功率依赖模型能力，
  而立项目标 7 恰恰要在「不同模型」上评测易用性；
- 需要沙箱：Workers 上是 Dynamic Workers（open beta、付费计划），自有机房上要跑 Deno / isolated-vm，运维与安全面都变大。

生成器已经把「操作 → 请求」做成了数据（`tools.json`），加一个 `search(code)` / `execute(code)` profile 只是再套一层：
spec 已在服务端、`execute` 里暴露一个 `jinshuju.request(op, args)`。等评测体系有了基线、沙箱方案定了再做，用 URL 或 header 选 profile。

## 6. 风险与待确认

| 事项                                                                                                                              | 影响                                                                                                                              | 建议                                                                                      |
| --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `account.jinshuju.net` 是否校验 RFC 8707 `resource` 参数 / 令牌 audience                                                          | MCP 客户端会带 `resource=https://mcp.jinshuju.net/mcp`；实测授权端点对未知 resource 不报错（直接转登录），但 token 端点行为未验证 | 上线前用真实客户端走一遍；若按 audience 校验需在 AS 登记新 resource                       |
| 2026-07-28 废弃动态注册、推荐 Client ID Metadata Documents                                                                        | 12 个月过渡期内 DCR 仍可用                                                                                                        | AS 后续支持 CIMD（后端任务）                                                              |
| `GET /me` 需要 `users` scope                                                                                                      | scope 不足时返回 403 而非 401，本服务视为令牌有效                                                                                 | 已按「只有 401 才无效」处理；可换成更轻的探测端点                                         |
| 限流按令牌每小时计数                                                                                                              | 校验调用也计数                                                                                                                    | 已缓存 5 分钟；企业账户默认额度较大                                                       |
| 现有 builtin 的 `context` 参数（每个工具都要求模型写「用户想做什么」）                                                            | 用于分析用户意图；新服务默认没有                                                                                                  | 产品决定是否保留：可在 overlay 里给所有工具加一个可选参数并以 header 转给 API             |
| `prepare_*_upload` 改为 `upload_*`（直接上传）；`update_entry` 不再提供 PUT 整体覆盖；7 个 prompt / 52 个字段类型 resource 未移植 | 少数依赖这些细节的用法要调整                                                                                                      | 预签名上传若仍需要，应作为 API v1 接口补进 openapi.yaml；prompt 可按需用 overlay 或代码补 |
| claude.ai 对 2026-07-28 的支持进度                                                                                                | 不影响：SDK 对旧握手按无状态兜底，与 builtin 行为一致                                                                             | 上线前用 claude.ai / Cursor / Claude Code 各连一次                                        |
| 表格的数据 / 视图 / 评论操作（28 个）未暴露                                                                                       | 与 builtin 一致（builtin 也只有 5 个表格工具）                                                                                    | 产品需要时在 overlay 的 include 里加一行即可                                              |

## 7. 评测方案（后续任务）

目标 7 要的是「真实用例 + 多模型 + 打分 + 持久化」。建议：

1. **样本集**：从 builtin MCP 的历史会话抽 30–50 个任务，按类别（找表单、读数据、统计、建表单、改设置、批量写入）分层，
   每个任务写成「自然语言 + 期望断言」（MCP-Atlas 的 claims rubric 做法：最终答案要满足哪些事实、应调用哪些工具、不应调用哪些）。
2. **运行器**：用 Claude Agent SDK（或任意支持 MCP 的 agent loop）连本服务与 builtin，分别在 3–4 个模型上跑；
   记录工具调用序列、token、轮次、错误重试次数。
3. **打分**：断言通过率为主，辅以 token / 轮次；LLM-as-judge 只用于开放式答案并固定 judge 模型。
4. **持久化**：结果写进一张金数据表单（本服务自己就能写），周报取数。
